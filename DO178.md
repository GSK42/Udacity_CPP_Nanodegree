# Part 1 – Fundamentals of DO-178C

## 1\. Introduction to DO-178C

### 1.1 What Is DO-178C?

DO-178C is an internationally recognized guidance document for developing airborne software that can be accepted as part of an aircraft certification program.

It provides a systematic framework for demonstrating that airborne software performs its intended functions and does not introduce unacceptable safety risks.

It addresses the complete software lifecycle, including:

- Planning
- Requirements development
- Software architecture and design
- Coding
- Integration
- Verification
- Testing
- Configuration management
- Quality assurance
- Certification evidence

The central philosophy is that software safety cannot be established simply by showing that a program works during normal operation.

Instead, the development organization must demonstrate that:

1. Software requirements correctly describe the intended functionality.
2. Requirements are sufficiently detailed and testable.
3. Software design correctly implements the requirements.
4. Source code correctly implements the design.
5. Verification demonstrates compliance with requirements.
6. Testing demonstrates correct behavior under expected and abnormal conditions.
7. Unintended functionality and unintended code are identified and addressed.
8. All development and verification activities are properly documented.
9. The final software product corresponds to the verified configuration.

### 1.2 Why Is DO-178C Necessary?

Consider an aircraft flight-control computer.

The software may control:

- Elevator movement
- Rudder movement
- Aileron movement
- Flight-control surface positioning
- Aircraft stability functions
- Pilot input processing

A software defect could potentially cause an incorrect flight-control command.

For example, suppose the aircraft's flight-control software receives an angle-of-attack measurement.

The software is expected to:

1. Receive the sensor input.
2. Validate the measurement.
3. Calculate the required control response.
4. Generate an appropriate output.
5. Monitor abnormal conditions.

If a programming error causes the software to interpret a sensor value incorrectly, the system could generate an unsafe output.

Traditional software testing may not identify every possible defect.

DO-178C addresses this problem by requiring a disciplined development and verification process with objective evidence.

### 1.3 What DO-178C Does Not Do

DO-178C does not:

- Guarantee that software is completely defect-free.
- Prescribe a specific programming language.
- Require a particular software development methodology.
- Mandate a particular operating system.
- Require a particular testing tool.
- Define the aircraft's complete system safety assessment.
- Replace hardware development assurance.
- Automatically certify an aircraft or avionics product.

It provides a framework for demonstrating software development assurance.

### 1.4 DO-178C Versus Traditional Software Development

| Traditional Software Development | DO-178C-Oriented Development |
| --- | --- |
| Focus on working functionality | Focus on functionality and assurance |
| Testing may be informal | Verification objectives are defined |
| Requirements may be flexible | Requirements must be controlled |
| Code reviews vary by project | Reviews and analyses are planned |
| Documentation may be optional | Lifecycle data must be maintained |
| Testing may focus on normal behavior | Requirements-based testing includes abnormal behavior |
| Traceability may be limited | Bidirectional traceability is established |
| Defects may be managed informally | Defects and problem reports are controlled |
| Release may depend on successful testing | Release depends on completion of applicable objectives |

The most important difference is that DO-178C requires evidence of how the software was developed and verified, not merely evidence that the software runs.

## 2\. Purpose and Scope

### 2.1 Primary Purpose

The primary purpose of DO-178C is to provide guidance for demonstrating that airborne software satisfies its intended functions with an assurance level appropriate to the consequences of software failure.

It applies to software developed for airborne systems and equipment.

Examples include:

- Flight management systems
- Flight control systems
- Autopilot systems
- Engine control systems
- Navigation systems
- Communication systems
- Cockpit display systems
- Aircraft monitoring systems
- Landing gear control systems
- Environmental control systems

### 2.2 Software Lifecycle Coverage

DO-178C addresses the following major processes:

1. Planning process
2. Software development process
3. Software verification process
4. Software configuration management process
5. Software quality assurance process
6. Certification liaison process

These processes are interconnected. Verification, for example, is not something that should only begin after coding is complete.

### 2.3 Applicability

DO-178C is used in connection with certification of airborne systems and equipment.

The FAA recognizes DO-178C through Advisory Circular AC 20-115D as an acceptable means of compliance for applicable software certification activities.

The advisory circular is guidance rather than a regulation in itself.

## 3\. Regulatory Framework

### 3.1 Organizations Involved

Several organizations participate in the airborne software certification ecosystem.

**RTCA**

The Radio Technical Commission for Aeronautics develops technical standards and guidance used in aviation.

RTCA published DO-178C.

**EUROCAE**

The European Organisation for Civil Aviation Equipment develops aviation technical standards.

The European counterpart to DO-178C is ED-12C.

**FAA**

The Federal Aviation Administration is the civil aviation authority in the United States.

It establishes certification requirements and recognizes acceptable means of demonstrating compliance.

**EASA**

The European Union Aviation Safety Agency performs a corresponding certification and regulatory role in Europe.

### 3.2 DO-178C and Advisory Guidance

DO-178C is not itself a federal regulation.

In the United States, FAA AC 20-115D recognizes DO-178C and its associated supplements as an acceptable means of showing compliance with applicable airworthiness regulations.

An applicant may propose an alternative means of compliance, subject to acceptance by the relevant authority.

## 4\. Software Development Assurance Levels

One of the most important concepts in DO-178C is the Software Level, commonly called the Design Assurance Level (DAL) in practical avionics discussions.

The software level determines the rigor of the applicable software development and verification objectives.

DO-178C identifies five software levels:

- Level A
- Level B
- Level C
- Level D
- Level E

### 4.1 Why Are Software Levels Necessary?

Not all airborne software has the same safety significance.

Consider two examples.

**Example A: Flight Control Software**

A defect in software controlling aircraft flight surfaces could contribute to a catastrophic aircraft condition.

This software may require Level A assurance.

**Example B: Passenger Entertainment Software**

A defect in an entertainment application may inconvenience passengers without affecting aircraft safety.

It may not require DO-178C assurance at all, depending on the system boundary and certification assessment.

The level is determined through system safety assessment and allocation of software assurance requirements.

### 4.2 The Five Software Levels

| Software Level | Failure Condition Classification | Description |
| --- | --- | --- |
| Level A | Catastrophic | Software failure could contribute to a catastrophic failure condition. |
| Level B | Hazardous / Severe-Major | Software failure could contribute to a hazardous or severe-major failure condition. |
| Level C | Major | Software failure could contribute to a major failure condition. |
| Level D | Minor | Software failure could contribute to a minor failure condition. |
| Level E | No Safety Effect | Software failure has no effect on aircraft operational safety. |

### 4.3 Assurance Rigor

Level A has the most demanding set of objectives.

As the software level decreases:

- The number of applicable objectives generally decreases.
- Some verification independence requirements are reduced.
- Structural coverage requirements become less extensive.
- The overall assurance burden decreases.

This does not mean that Level D software can be developed carelessly. All applicable objectives must still be satisfied.

### 4.4 Software Level Versus Software Complexity

An important misconception is that a complicated program automatically receives Level A.

That is incorrect.

The software level is based on the safety assessment and the contribution of the software to aircraft-level failure conditions.

A relatively small software component may require Level A if its failure can contribute to a catastrophic condition.

Conversely, a very large application may have no aircraft safety effect.

### 4.5 Software Level and Independence

DO-178C includes independence requirements for certain verification objectives.

For higher assurance levels, the person or team performing specified verification activities must be independent of the person or team responsible for the corresponding development activity.

For example:

- A developer writes a software module.
- A separate verification engineer reviews the implementation.
- The verification engineer checks compliance with requirements.
- The results are documented independently.

Independence reduces the likelihood that the same assumptions or misunderstandings affect both development and verification.

## 5\. Relationship Between System Safety and Software Assurance

### 5.1 System Safety Comes First

DO-178C software levels are not selected arbitrarily.

They are derived from the system safety assessment process.

The general sequence is:

1. Identify aircraft functions.
2. Identify possible failure conditions.
3. Assess the severity of each failure condition.
4. Determine the safety objectives.
5. Allocate safety requirements to system components.
6. Allocate software assurance levels to software components.
7. Define the development and verification rigor.

### 5.2 Example: Aircraft Landing Gear Control

Consider a landing gear control system.

The system contains:

- Landing gear position sensors
- Control computer
- Actuator interface
- Cockpit indication
- Warning logic

Potential software failures include:

- Incorrect gear position indication
- Failure to process a gear command
- Incorrect warning generation
- Incorrect sensor validity assessment

The system safety assessment determines the effects of these failures.

Software level allocation then follows the resulting safety classification and approved development assurance strategy.

### 5.3 Important Distinction

DO-178C does not independently prove that the aircraft is safe.

It provides assurance about the software development and verification processes.

Aircraft-level safety must also consider:

- Hardware failures
- Sensor failures
- Electrical power failures
- Mechanical failures
- Common-cause failures
- Environmental conditions
- Human factors
- System architecture

This distinction is essential when working with certification authorities.

# Part 2 – DO-178C Software Lifecycle

## 6\. Software Lifecycle Overview

DO-178C organizes development into processes that produce defined outputs and verification evidence.

The software lifecycle can be divided into the following major stages:

1. Planning
2. Software requirements development
3. Software design
4. Coding
5. Integration
6. Verification
7. Configuration management
8. Quality assurance
9. Certification liaison

### 6.1 Development Flow

The V-model is a useful way to understand the relationship between development and verification.

| Development Activity | Corresponding Verification |
| --- | --- |
| System requirements | System-level validation and verification |
| High-level software requirements | High-level requirements verification |
| Software architecture | Architecture and integration verification |
| Low-level software requirements | Low-level requirements verification |
| Source code | Source code verification |
| Executable software | Software integration and requirements-based testing |

The V-model is an explanatory development model. DO-178C does not mandate that every project use a specific V-model implementation.

### 6.2 Outputs of the Lifecycle

Typical lifecycle outputs include:

- Plans
- Requirements documents
- Design descriptions
- Source code
- Executable object code
- Test procedures
- Test results
- Review records
- Analysis reports
- Coverage reports
- Configuration records
- Problem reports
- Software accomplishment summary

These outputs collectively form the evidence that the software has satisfied its applicable objectives.

## 7\. Planning Process

### 7.1 Importance of Planning

Planning is one of the most critical activities in a DO-178C project.

Before software development begins, the organization must establish how the project will satisfy the applicable objectives.

Poor planning often leads to:

- Missing requirements
- Incomplete test coverage
- Unclear responsibilities
- Uncontrolled changes
- Missing documentation
- Certification delays
- Expensive rework

### 7.2 Main Planning Documents

#### 1\. Plan for Software Aspects of Certification (PSAC)

The PSAC describes the proposed software development and assurance approach.

It typically identifies:

- Software overview
- Software level
- Development environment
- Applicable DO-178C objectives
- Development processes
- Verification approach
- Configuration management approach
- Quality assurance approach
- Certification authority coordination

The PSAC is particularly important because it explains how the applicant intends to demonstrate compliance.

#### 2\. Software Development Plan (SDP)

The SDP defines how software development will be performed.

It describes:

- Development activities
- Responsibilities
- Development environment
- Software lifecycle
- Requirements processes
- Design processes
- Coding processes
- Integration activities

#### 3\. Software Verification Plan (SVP)

The SVP describes how software verification will be conducted.

It defines:

- Verification methods
- Review activities
- Analysis activities
- Test procedures
- Test environments
- Verification independence
- Verification records

#### 4\. Software Configuration Management Plan (SCMP)

The SCMP explains how software configuration items will be identified, controlled, tracked, and released.

#### 5\. Software Quality Assurance Plan (SQAP)

The SQAP explains how software quality assurance activities will be performed.

### 7.3 Planning Document Relationship

| Document | Main Question Answered |
| --- | --- |
| PSAC | How will certification objectives be satisfied? |
| SDP | How will software be developed? |
| SVP | How will software be verified? |
| SCMP | How will configurations and changes be controlled? |
| SQAP | How will process compliance be assured? |

### 7.4 Planning Approval and Coordination

Planning documents must be reviewed and maintained throughout the project.

If the project changes its development methodology, verification strategy, tools, or software architecture, the plans may need revision.

For example, if a project initially plans manual testing but later introduces automated test generation, the verification approach and tool qualification strategy must be evaluated.

### 7.5 Practical Example

Suppose an avionics company is developing a flight management software component at Level B.

The planning phase should establish:

- Applicable Level B objectives
- Requirements development process
- Coding standards
- Verification strategy
- Required independence
- Testing strategy
- Structural coverage strategy
- Configuration management procedures
- Software tool qualification needs
- Certification deliverables

The company should not wait until the end of development to determine how it will prove compliance.

## 8\. Software Development Standards

DO-178C expects development activities to follow defined standards.

These standards establish consistent methods for producing requirements, designs, and source code.

### 8.1 Software Requirements Standards

A requirements standard defines:

- Required requirement structure
- Requirement numbering
- Requirement writing rules
- Requirement review criteria
- Traceability expectations
- Change control

A good requirement should be:

- Clear
- Unambiguous
- Verifiable
- Consistent
- Correct
- Traceable
- Feasible

### 8.2 Software Design Standards

A design standard defines:

- Architecture documentation
- Module decomposition
- Interface descriptions
- Data structures
- Control flow
- Error handling
- Resource management

### 8.3 Software Coding Standards

A coding standard defines:

- Naming conventions
- Data types
- Variable declaration
- Function structure
- Error handling
- Memory management
- Defensive programming practices
- Restricted language features

For C and C++, the standard may address:

- Pointer usage
- Dynamic memory allocation
- Type conversions
- Integer overflow risks
- Uninitialized variables
- Undefined behavior
- Recursion
- Concurrency

### 8.4 Why Coding Standards Matter

Consider the following illustrative C code:

c

```c
int speed;

if (speed > 250)
{
    alarm = 1;
}
```

The variable `speed` has not been initialized.

The software may behave unpredictably depending on the execution environment and language implementation.

A coding standard and source code verification process should prevent or identify this type of problem.

A coding standard alone, however, does not demonstrate compliance. The project must verify that the standard has been followed.

## 9\. Requirements-Based Development

Requirements are the foundation of DO-178C.

The software must be developed from controlled requirements rather than from informal assumptions.

### 9.1 Requirements Hierarchy

A typical hierarchy is:

text

```text
Aircraft / System Requirements
            |
            v
High-Level Software Requirements (HLR)
            |
            v
Low-Level Software Requirements (LLR)
            |
            v
Source Code
            |
            v
Executable Software
```

### 9.2 High-Level Software Requirements

High-level software requirements describe what the software must do.

They are derived from system requirements and allocated system functionality.

Example:

**HLR-001: Airspeed Monitoring**

The software shall receive airspeed measurements from the air data system and provide validated airspeed information to the flight management function.

**HLR-002: Invalid Data Detection**

The software shall identify airspeed measurements that fail the specified validity criteria.

**HLR-003: Data Update**

The software shall update the airspeed output according to the specified update rate.

These requirements describe observable behavior.

### 9.3 Low-Level Software Requirements

Low-level software requirements describe the detailed functionality needed to implement the high-level requirements.

For example:

**LLR-001**

The software shall read the airspeed input from the specified interface variable.

**LLR-002**

The software shall compare the input value against the defined minimum and maximum limits.

**LLR-003**

The software shall set the airspeed validity flag to invalid when the input violates the specified validity criteria.

**LLR-004**

The software shall update the output airspeed variable when the input passes the validity checks.

### 9.4 Good and Bad Requirements

Bad requirement:

"The software should process airspeed quickly."

Problems:

- What does quickly mean?
- What is the maximum processing time?
- What is the input rate?
- How is compliance verified?

Improved requirement:

"The software shall update the validated airspeed output within 20 milliseconds of receiving a valid input sample."

This is measurable and testable, assuming the timing requirement is supported by the system design.

### 9.5 Requirements Verification

Requirements should be reviewed for:

1. Correctness
2. Completeness
3. Consistency
4. Accuracy
5. Verifiability
6. Traceability
7. Compliance with system requirements

Requirements verification should identify ambiguous, missing, conflicting, or unnecessary requirements.

## 10\. Software Architecture and Design

Software architecture describes how the software is organized into components and how those components interact.

### 10.1 Architectural Decomposition

A software system may be divided into:

- Modules
- Components
- Processes
- Tasks
- Functions
- Data interfaces
- Communication channels

For example, an aircraft engine control system might contain:

1. Sensor input processing
2. Engine parameter monitoring
3. Fuel control calculations
4. Engine limit protection
5. Actuator command generation
6. Fault monitoring

### 10.2 Architecture Objectives

The software architecture should ensure:

- Functional correctness
- Clear interfaces
- Controlled data flow
- Appropriate resource allocation
- Defined execution behavior
- Compatibility with system requirements
- Manageable complexity

### 10.3 Interface Design

Interfaces are particularly important in avionics software.

A software interface may specify:

- Input parameters
- Output parameters
- Data types
- Units
- Valid ranges
- Update rates
- Error conditions
- Initialization behavior

Example:

| Parameter | Type | Description |
| --- | --- | --- |
| Airspeed | Integer | Measured airspeed |
| Validity | Boolean | Input validity indicator |
| Timestamp | Integer | Measurement timestamp |
| Output speed | Integer | Processed airspeed |
| Fault flag | Boolean | Indicates an input fault |

### 10.4 Architecture Verification

Architecture verification checks that:

- All high-level requirements are allocated.
- Components are correctly identified.
- Interfaces are defined.
- Data flows are understood.
- Timing and resource requirements are addressed.
- Architectural constraints are satisfied.

A design review should identify missing functionality, unintended behavior, and architectural inconsistencies.

## 11\. Source Code Development

Source code is the implementation of the software design and low-level requirements.

DO-178C does not mandate a specific programming language.

Common languages include:

- C
- C++
- Ada
- Assembly language

### 11.1 Coding Process

A typical coding process involves:

1. Review the applicable low-level requirements.
2. Review the software architecture.
3. Implement the required functionality.
4. Follow the coding standard.
5. Perform code reviews.
6. Verify the source code.
7. Compile the software.
8. Integrate the software.

### 11.2 Source Code Verification

Source code verification evaluates whether the implementation correctly satisfies the low-level requirements and conforms to the applicable coding and design standards.

It may involve:

- Code reviews
- Static analysis
- Data flow analysis
- Control flow analysis
- Compiler output examination
- Other verification techniques

### 11.3 Source Code and Object Code

Source code is not the final executable product.

The compiler transforms source code into object code or executable code.

Therefore, the project must consider whether the generated object code contains functionality that is not adequately represented by the source code.

This is especially important when using:

- Optimizing compilers
- Complex compiler features
- Assembly language
- Inline assembly
- Compiler-generated runtime code

### 11.4 Compiler Considerations

A compiler defect or incorrect compiler configuration can affect the generated executable.

The project should establish appropriate confidence in the development tools and verify the resulting software.

Tool qualification is discussed later in this document.

# Part 3 – Verification and Testing

## 12\. Software Verification

### 12.1 What Is Verification?

Verification is the process of determining whether the software development outputs satisfy their applicable requirements and standards.

In simple terms:

**Verification asks: Did we build the software correctly?**

Verification is one of the most important aspects of DO-178C.

The objective is not merely to execute the software and observe whether it works. The project must produce objective evidence that the software satisfies its specified requirements.

### 12.2 Verification Activities

Verification generally consists of four major categories:

1. Reviews
2. Analyses
3. Testing
4. Structural coverage analysis

| Activity | Purpose |
| --- | --- |
| Requirements review | Check requirement quality |
| Design review | Check architectural correctness |
| Code review | Check implementation correctness |
| Static analysis | Identify potential defects without execution |
| Requirements-based testing | Demonstrate required behavior |
| Structural coverage | Identify unexecuted software structures |

### 12.3 Verification at Each Development Stage

| Development Output | Verification Activity |
| --- | --- |
| Software plans | Plan reviews |
| High-level requirements | Requirements reviews and analyses |
| Software architecture | Architecture reviews and analyses |
| Low-level requirements | Detailed requirements reviews |
| Source code | Code reviews and analyses |
| Executable software | Integration and requirements-based testing |
| Final software | Coverage analysis and final verification |

### 12.4 Verification Independence

Independence means that specified verification activities are performed independently from the corresponding development activities.

The extent of required independence depends on the software level and the applicable objective.

For example, for an applicable Level A objective, the developer who wrote the code should not be the sole person responsible for verifying that code.

This provides an additional layer of protection against human error.

### 12.5 Verification Evidence

Every verification activity should produce appropriate records.

Examples:

- Review checklists
- Review comments
- Test procedures
- Test results
- Analysis reports
- Defect reports
- Coverage reports
- Verification completion records

The records should identify the item verified, the method used, the results, and any problems found.

## 13\. Reviews and Analyses

Reviews and analyses are essential because not every defect can be detected through execution testing.

### 13.1 Requirements Reviews

Requirements reviews examine whether requirements are:

- Correct
- Complete
- Consistent
- Unambiguous
- Verifiable
- Traceable

Example:

Requirement:

"The software shall generate an alarm when engine temperature becomes excessive."

Review findings:

- What is the temperature threshold?
- Is the threshold configurable?
- How long must the condition persist?
- What happens when the sensor becomes invalid?
- How quickly must the alarm be generated?

A review identifies these missing details before implementation.

### 13.2 Design Reviews

Design reviews evaluate whether the architecture and detailed design correctly implement the software requirements.

Typical review areas:

- Functional allocation
- Module decomposition
- Interface consistency
- Data flow
- Control flow
- Timing
- Error handling
- Resource utilization

### 13.3 Code Reviews

Code reviews examine whether source code conforms to the applicable requirements and standards.

Typical concerns include:

- Incorrect calculations
- Incorrect comparisons
- Uninitialized variables
- Incorrect data types
- Array boundary errors
- Pointer problems
- Incorrect exception handling
- Unintended functionality
- Missing error handling

### 13.4 Static Analysis

Static analysis examines software without executing it.

Examples include:

- Control flow analysis
- Data flow analysis
- Dead code analysis
- Unreachable code analysis
- Variable initialization analysis
- Range analysis
- Coding standard compliance analysis

Static analysis is useful for identifying potential defects early in the development process.

However, a static analysis tool does not automatically replace all required reviews or testing.

### 13.5 Data Flow Analysis

Data flow analysis examines how data is defined, modified, and used.

Consider:

c

```c
int temperature = 100;

temperature = 120;
temperature = 140;

alarm = (temperature > 130);
```

The initial values may be overwritten before being used.

Analysis can help identify unnecessary assignments and unexpected data dependencies.

### 13.6 Control Flow Analysis

Control flow analysis examines the possible paths through a program.

For example:

c

```c
if (temperature > 150)
{
    alarm = 1;
}
else
{
    alarm = 0;
}
```

The analysis identifies possible execution paths and helps establish whether the required conditions have been verified.

## 14\. Software Testing

### 14.1 What Is Requirements-Based Testing?

Requirements-based testing demonstrates that the software behaves according to its requirements.

Every applicable requirement should have an appropriate verification method.

For executable requirements, testing is generally a key verification method.

Testing should demonstrate:

- Expected functionality
- Boundary behavior
- Invalid input handling
- Abnormal conditions
- Error handling
- Timing behavior where applicable

### 14.2 Requirements-Based Test Development

A test should be developed from an approved requirement.

For example:

**Requirement HLR-001**

The software shall generate an over-temperature warning when the validated temperature exceeds 150°C.

Possible tests:

| Test | Input Temperature | Expected Output |
| --- | --- | --- |
| TC-001 | 100°C | No warning |
| TC-002 | 149°C | No warning |
| TC-003 | 150°C | No warning, if requirement specifies exceeds |
| TC-004 | 151°C | Warning |
| TC-005 | Invalid sensor data | Defined invalid-data response |

The expected result must be derived from the actual approved requirement and interface specification.

### 14.3 Normal Testing

Normal testing checks the software under expected operating conditions.

Examples:

- Normal sensor readings
- Normal aircraft operating parameters
- Standard communication messages
- Typical pilot inputs

### 14.4 Boundary Testing

Boundary testing checks the behavior at the limits of acceptable input values.

Suppose the valid airspeed range is 0–500 knots.

Relevant test values may include:

- -1
- 0
- 1
- 499
- 500
- 501

Boundary tests are useful because many software defects occur at range limits.

### 14.5 Robustness Testing

Robustness testing evaluates the response to abnormal or unexpected inputs.

Examples:

- Missing sensor data
- Out-of-range values
- Invalid communication messages
- Incorrect data formats
- Timing violations
- Repeated inputs
- Unexpected state transitions

### 14.6 Test Procedures

A well-defined test procedure generally includes:

1. Test identification
2. Requirement reference
3. Test objective
4. Initial conditions
5. Test environment
6. Input values
7. Execution steps
8. Expected results
9. Actual results
10. Pass/fail status
11. Test evidence
12. Problem report references, where applicable

### 14.7 Test Environment

Testing may be conducted using:

- Host computers
- Target hardware
- Software simulators
- Hardware-in-the-loop systems
- Integration test benches
- Test harnesses
- Instrumentation equipment

The project must demonstrate that the test environment is suitable for the verification objective.

Differences between the host and target environments must be considered, particularly where they affect timing, numerical behavior, memory, hardware interfaces, or compiler behavior.

## 15\. Structural Coverage Analysis

Structural coverage is a fundamental DO-178C topic.

It evaluates which parts of the software structure were exercised during requirements-based testing.

The purpose is to identify software structures that were not executed and determine whether additional testing or analysis is necessary.

### 15.1 Why Is Structural Coverage Required?

Imagine a software function containing 100 executable statements.

Requirements-based testing exercises only 80 of those statements.

This raises an important question:

What happens in the remaining 20 statements?

They may represent:

- Missing test cases
- Unimplemented requirements
- Dead code
- Deactivated code
- Defensive functionality
- Unintended functionality

Structural coverage analysis helps identify these situations.

### 15.2 Three Major Coverage Concepts

#### Statement Coverage

Determines whether each executable statement has been executed.

Illustrative example:

text

```text
Executed statements:   7
Total statements:     10
Statement coverage:   70%
```

#### Decision Coverage

Determines whether each decision outcome has been exercised.

For a Boolean decision, both TRUE and FALSE outcomes should be demonstrated.

#### Modified Condition/Decision Coverage (MC/DC)

Demonstrates that each condition in a decision can independently affect the decision outcome.

### 15.3 Statement Coverage

Statement coverage determines whether every executable statement has been executed.

Example:

c

```c
if (temperature > 150)
{
    alarm = 1;
}

status = 0;
```

Testing with temperature = 160 executes the alarm assignment and the status assignment.

However, a test with temperature = 100 does not execute the alarm assignment.

Additional testing may be needed.

### 15.4 Decision Coverage

Decision coverage checks whether both possible outcomes of a decision have been exercised.

Example:

c

```c
if (temperature > 150)
{
    alarm = 1;
}
else
{
    alarm = 0;
}
```

The test set should demonstrate:

- True outcome
- False outcome

### 15.5 MC/DC

MC/DC stands for Modified Condition/Decision Coverage.

It is particularly important for Level A software.

Consider:

c

```c
if ((A > 10) && (B < 50))
{
    alarm = 1;
}
```

The decision contains two conditions:

- Condition A: A is greater than 10.
- Condition B: B is less than 50.

MC/DC requires demonstrating that each condition can independently affect the decision outcome while the other condition is held appropriately constant.

Illustrative test set:

| Test | A Condition | B Condition | Overall Decision |
| --- | --- | --- | --- |
| 1 | True | True | True |
| 2 | False | True | False |
| 3 | True | False | False |

Test 1 versus Test 2 demonstrates the independent effect of A.

Test 1 versus Test 3 demonstrates the independent effect of B.

### 15.6 Coverage Requirements by Software Level

| Software Level | Structural Coverage Expectation |
| --- | --- |
| Level A | Statement, decision and MC/DC |
| Level B | Statement and decision |
| Level C | Statement |
| Level D | No specific structural coverage objective equivalent to Levels A–C |
| Level E | No DO-178C software objectives |

These are the standard structural coverage distinctions. The exact applicable objectives and treatment must be checked against the standard.

### 15.7 What Happens When Coverage Is Missing?

Suppose Level A software has 95% statement coverage.

That does not mean the software is 95% compliant.

The uncovered structures must be investigated.

Possible actions:

- Add test cases.
- Correct incomplete requirements.
- Investigate unintended code.
- Remove genuinely unnecessary code through controlled changes.
- Provide an acceptable analysis where justified.

### 15.8 Dead Code and Deactivated Code

**Dead code:** Code that cannot execute in the target software configuration.

**Deactivated code:** Code that can execute but is not intended to execute in the particular software configuration or operating mode.

Both require careful investigation.

Dead code is generally expected to be eliminated.

Deactivated code requires appropriate identification, control, and verification.

## 16\. Requirements Traceability

Traceability is the ability to establish relationships between software requirements, design, code, and verification evidence.

It is essential for demonstrating that requirements have been implemented and verified.

### 16.1 Forward Traceability

Forward traceability follows the development process.

For example:

text

```text
System Requirement
       |
       v
High-Level Requirement
       |
       v
Low-Level Requirement
       |
       v
Source Code
       |
       v
Test Case
```

It answers:

"Where was this requirement implemented and tested?"

### 16.2 Backward Traceability

Backward traceability follows the relationship in reverse.

text

```text
Source Code
     |
     v
Low-Level Requirement
     |
     v
High-Level Requirement
     |
     v
System Requirement
```

It answers:

"Why does this code exist?"

### 16.3 Example Traceability Matrix

| Requirement | Design | Code | Test | Status |
| --- | --- | --- | --- | --- |
| HLR-001 | DES-001 | MOD-001 | TC-001 | Verified |
| HLR-002 | DES-002 | MOD-002 | TC-002 | Verified |
| HLR-003 | DES-003 | MOD-003 | TC-003 | Verified |
| HLR-004 | DES-004 | MOD-004 | TC-004 | Pending |

This is an illustrative traceability matrix.

### 16.4 Why Bidirectional Traceability Matters

Forward traceability ensures requirements are implemented and verified.

Backward traceability helps identify:

- Unnecessary code
- Unintended functionality
- Missing design justification
- Unjustified software components

Traceability also supports change impact analysis.

### 16.5 Traceability Tools

Commonly used tools include:

- IBM DOORS
- Jama Connect
- Polarion
- Codebeamer
- Requirements management databases
- Controlled spreadsheets

A tool can support traceability, but using the tool does not automatically satisfy DO-178C objectives.

The project must verify the integrity and correctness of the information.

### 17.1 What Is Configuration Management?

Configuration management ensures that all software products and lifecycle data are identified, controlled, and maintained throughout the project.

The purpose is to ensure that the software being tested, reviewed, and delivered is the same controlled configuration.

Examples:

- Source code baseline
- Test baseline
- Software release baseline

### 17.4 Change Management

1. Open a problem report.

4. Perform impact analysis.

A controlled development environment should establish:

- Authorized access
- Change identification

## 18\. Software Quality Assurance

### 18.1 Purpose

Software Quality Assurance (SQA) provides confidence that the software lifecycle processes are being followed and that the resulting lifecycle data are properly controlled.

SQA is not simply a testing activity.

Testing verifies software behavior.

SQA verifies adherence to the defined processes and plans.

### 18.2 Main SQA Responsibilities

Typical SQA activities include:

- Reviewing development process compliance
- Reviewing verification process compliance
- Checking adherence to standards
- Auditing lifecycle records
- Checking configuration management
- Monitoring problem reporting
- Confirming that required reviews occurred
- Monitoring corrective actions
- Reporting noncompliance

### 18.3 SQA Versus Software Verification

| Software Verification | Software Quality Assurance |
| --- | --- |
| Checks whether software satisfies requirements | Checks whether processes and procedures are followed |
| Examines design and code | Examines lifecycle compliance |
| Performs tests and analyses | Performs audits and process reviews |
| Identifies functional defects | Identifies process deficiencies |
| Produces verification evidence | Produces quality assurance evidence |

### 18.4 Example SQA Audit

An SQA engineer may select a software module and check:

1. Was the requirement approved?
2. Was the design reviewed?
3. Was the code developed according to the coding standard?
4. Was the code verified?
5. Was the test procedure approved?
6. Were the tests executed?
7. Was the structural coverage evaluated where applicable?
8. Were defects documented?
9. Were changes controlled?
10. Is the module included in the correct baseline?

The purpose is to verify that the planned lifecycle was followed.

### 18.5 Nonconformance Management

If an audit identifies a missing review record, SQA should document the finding.

The project must:

- Assess the impact.
- Identify affected deliverables.
- Determine corrective actions.
- Re-perform activities if necessary.
- Verify closure.

A missing record cannot simply be recreated as though the original activity had occurred.

# Part 5 – Advanced DO-178C Topics

## 21\. Software Tool Qualification – DO-330

### 21.1 Why Tool Qualification Is Important

Modern avionics software development uses many automated tools.

Examples:

- Compilers
- Code generators
- Static analysis tools
- Requirements management tools
- Test execution tools
- Coverage analysis tools
- Model-based development tools
- Configuration management tools

These tools can affect the integrity of software development and verification evidence.

A defective tool could introduce an error or fail to detect an existing error.

DO-330 provides guidance for software tool qualification.

### 21.2 What Is Tool Qualification?

Tool qualification provides evidence that a tool performs its intended function with an acceptable level of confidence when used in the specified environment.

It is important to understand that not every tool used in a DO-178C project needs qualification.

The need depends on how the tool is used and whether its output is independently verified.

### 21.3 Tool Categories

**Development Tools**

These tools can generate or modify software products.

Examples:

- Code generators
- Model-based code generation tools
- Compilers
- Software development utilities

**Verification Tools**

These tools can automate verification activities.

Examples:

- Test coverage tools
- Static analysis tools
- Test result analysis tools
- Automated test generators

### 21.4 Tool Qualification Levels

DO-330 defines five Tool Qualification Levels (TQLs).

| Tool Level | General Assurance Rigor |
| --- | --- |
| TQL-1 | Highest |
| TQL-2 | Very high |
| TQL-3 | High |
| TQL-4 | Lower |
| TQL-5 | Lowest |

The applicable TQL is determined by the tool's intended use, the software level, and the consequences of an erroneous tool output.

It is not simply assigned based on whether a tool is a compiler, tester, or code generator.

### 21.5 Example: Test Coverage Tool

Suppose a project uses an automated coverage tool to demonstrate MC/DC coverage for Level A software.

If the tool incorrectly reports that all required conditions have been independently exercised, the project may accept software that has not actually satisfied the coverage objective.

The tool qualification strategy must address the risk that the tool could produce an incorrect result without detection.

### 21.6 Example: Compiler

A compiler converts source code into executable code.

A compiler error may introduce unintended executable behavior.

The project must establish appropriate confidence in the generated object code.

This may involve:

- Compiler qualification, where applicable
- Verification of compiler-generated output
- Appropriate testing
- Analysis of the development toolchain

The exact approach depends on the tool's use and the applicable qualification criteria.

### 21.7 Tool Qualification Documentation

Typical tool qualification evidence may include:

- Tool operational requirements
- Tool development and configuration information
- Tool verification evidence
- Tool configuration identification
- Tool qualification plan
- Tool qualification results
- Tool accomplishment summary

The specific data depend on the applicable TQL and DO-330 objectives.

## 22\. Model-Based Development – DO-331

### 22.1 What Is Model-Based Development?

Model-based development uses graphical or mathematical models to describe software behavior, architecture, or algorithms.

Instead of creating all software directly through hand-written source code, engineers create models that may be used for analysis, simulation, verification, or automatic code generation.

Examples of modeling environments include:

- MATLAB/Simulink
- Stateflow
- SCADE

### 22.2 Example

An engine control algorithm can be represented using a graphical model.

The model may contain:

- Sensor input blocks
- Mathematical calculation blocks
- Conditional logic
- State machines
- Output generation blocks

The model can be simulated before source code is generated.

### 22.3 Advantages

Model-based development can provide:

1. Visual representation of complex functionality.
2. Early simulation.
3. Easier identification of logical errors.
4. Reusable design components.
5. Automated code generation.
6. Better communication between engineers.
7. Improved consistency between design and implementation.

### 22.4 Certification Considerations

Model-based development does not eliminate DO-178C objectives.

The project must address:

- Model requirements
- Model verification
- Model standards
- Model traceability
- Generated code verification
- Code generator qualification where applicable
- Model-to-code consistency

### 22.5 Important Distinction

A simulation that demonstrates correct model behavior does not automatically demonstrate that the generated executable software behaves correctly.

The project must establish the necessary verification evidence for the actual software product.

DO-331 supplements DO-178C for model-based development and verification.

## 23\. Object-Oriented Technology – DO-332

### 23.1 What Is Object-Oriented Programming?

Object-oriented programming organizes software around objects and classes.

Common concepts include:

- Encapsulation
- Inheritance
- Polymorphism
- Dynamic binding
- Abstraction

Languages such as C++ and Java support object-oriented programming.

C++ is particularly relevant in some avionics software environments.

### 23.2 Example

An aircraft monitoring application may contain classes such as:

cpp

```cpp
class Sensor
{
public:
    virtual double readValue() = 0;
};

class TemperatureSensor : public Sensor
{
public:
    double readValue() override
    {
        return 120.0;
    }
};
```

The architecture uses inheritance and virtual functions.

### 23.3 Potential Benefits

Object-oriented programming can provide:

- Modularity
- Reusability
- Encapsulation
- Easier maintenance
- Clearer software architecture

### 23.4 Potential Certification Challenges

Some object-oriented features create additional verification challenges.

Examples:

- Dynamic dispatch
- Inheritance
- Virtual functions
- Dynamic memory allocation
- Complex object lifecycles
- Runtime type identification
- Exception handling

The project must demonstrate that the behavior of these features is adequately understood and verified.

### 23.5 DO-332

DO-332 provides additional guidance for object-oriented technology and related techniques.

It supplements the core DO-178C processes rather than replacing them.

The project should consider the effects of object-oriented features on requirements, architecture, implementation, testing, and structural coverage.

## 24\. Formal Methods – DO-333

### 24.1 What Are Formal Methods?

Formal methods use mathematical techniques to describe and verify software properties.

Instead of relying exclusively on testing, formal methods can demonstrate that certain properties hold under defined assumptions.

Examples include:

- Formal specification
- Mathematical proof
- Theorem proving
- Model checking
- Formal verification

### 24.2 Example

Suppose a software component must guarantee that an actuator command never exceeds a specified maximum.

A mathematical property could be:

$$
0 \leq Command \leq 100
$$

A formal verification approach may prove that the specified software logic maintains this property under the stated assumptions.

### 24.3 Benefits

Formal methods may help:

- Identify logical inconsistencies
- Demonstrate critical properties
- Reduce dependence on some testing activities
- Improve confidence in complex algorithms
- Verify specific safety-related behavior

### 24.4 Limitations

Formal verification does not automatically demonstrate that:

- The original requirements are correct.
- The system assumptions are valid.
- The software interfaces behave correctly.
- The compiler generates the intended executable.
- The aircraft system is safe.

The quality of the formal specification and the validity of its assumptions remain essential.

### 24.5 DO-333

DO-333 provides guidance for using formal methods in DO-178C projects.

It describes how formal methods may be used to satisfy or modify certain verification objectives when the required evidence is provided.

Formal methods are an alternative or supplementary verification technique, not a blanket exemption from software assurance.

## 25\. Independence Requirements

### 25.1 What Is Independence?

Independence means separating the performance of certain verification activities from the development activities being verified.

The goal is to reduce the possibility that the same person makes an error and then overlooks that error during verification.

### 25.2 Example

A developer writes a function that calculates engine temperature limits.

A separate verification engineer:

- Reviews the requirements.
- Examines the implementation.
- Develops test cases.
- Executes the tests.
- Reviews the results.

This separation can expose assumptions that the developer may have overlooked.

### 25.3 Independence Versus Organizational Separation

Independence does not necessarily mean that the verification engineer must work for a completely different company or department.

The important issue is whether the required verification activity is performed independently according to the applicable objectives and the project's approved processes.

### 25.4 Independence by Software Level

The need for independence varies with the assurance level.

Higher-level software has more stringent independence expectations.

Projects should identify the applicable independence objectives during planning rather than deciding informally during testing.

# Part 6 – Certification and Project Implementation

## 26\. DO-178C Certification Process

### 26.1 Overview

A DO-178C project normally follows a structured certification process.

1. **System safety assessment:** Determine the safety impact of software failure.
2. **Software level allocation:** Establish the required assurance level.
3. **Certification planning:** Prepare and coordinate the PSAC and supporting plans.
4. **Requirements development:** Develop and review software requirements.
5. **Design and implementation:** Establish architecture, detailed design and source code.
6. **Software verification:** Perform reviews, analyses and requirements-based testing.
7. **Coverage and problem resolution:** Complete structural coverage and resolve identified problems.
8. **Configuration and quality audits:** Verify the final controlled software configuration and process compliance.
9. **Certification evidence submission:** Provide the applicable lifecycle data and accomplishment records.
10. **Software approval:** Support the overall product or equipment certification process.

### 26.2 Certification Planning Review

The certification approach should be established early.

The project should identify:

- Certification basis
- Software level
- Software architecture
- Applicable objectives
- Development tools
- Verification methods
- Independence requirements
- Lifecycle data
- Certification authority involvement

### 26.3 Development Review

During development, the project produces requirements, design, source code, and verification records.

The development team must maintain traceability and configuration control throughout this period.

### 26.4 Verification Review

The verification team evaluates whether the applicable requirements and software structures have been adequately verified.

Open defects, failed tests, and coverage gaps must be investigated.

### 26.5 Final Certification Review

The final review determines whether the project has completed its planned lifecycle activities and has sufficient evidence to support its compliance claim.

A successful test run alone is not sufficient.

## 27\. Common DO-178C Compliance Problems

DO-178C projects can experience significant delays due to deficiencies in requirements, verification, and lifecycle documentation.

The following are common problem areas.

### 27.1 Poor Requirements Quality

**Problem:** Requirements are ambiguous or incomplete.

Example:

"The software shall respond quickly."

**Solution:** Specify measurable timing and observable behavior.

### 27.2 Missing Traceability

**Problem:** A source code module has no identifiable requirement.

**Risk:** The project cannot demonstrate why the code exists.

**Solution:** Establish and maintain bidirectional traceability.

### 27.3 Inadequate Test Coverage

**Problem:** Requirements-based tests do not exercise all required behavior.

**Solution:** Review requirements, develop appropriate tests, and perform structural coverage analysis.

### 27.4 Unresolved Coverage Gaps

**Problem:** Unexecuted statements or decisions remain unexplained.

**Solution:** Investigate every uncovered structure and determine whether additional tests, corrective action, or justified analysis is needed.

### 27.5 Incorrect Tool Qualification Strategy

**Problem:** The project assumes that all tools are automatically acceptable.

**Solution:** Evaluate tool usage and determine qualification requirements under DO-330.

### 27.6 Poor Configuration Management

**Problem:** The team tests one version of software but submits another.

**Solution:** Establish controlled baselines and reproducible release configurations.

### 27.7 Insufficient Verification Independence

**Problem:** Required verification is performed without the specified independence.

**Solution:** Establish independence responsibilities in the SVP.

### 27.8 Incomplete Problem Reports

**Problem:** Test failures are fixed informally without adequate records.

**Solution:** Establish controlled problem reporting, impact analysis, corrective action, and closure evidence.

### 27.9 Late Certification Involvement

**Problem:** The certification authority discovers major process issues near the end of the project.

**Solution:** Coordinate the certification strategy early and address questions throughout development.

### 27.10 Incomplete Lifecycle Data

**Problem:** The software works, but the project cannot produce sufficient supporting evidence.

**Solution:** Make lifecycle data production part of the normal engineering workflow.

## 28\. Practical Project Implementation

This section illustrates how a company could organize an actual DO-178C project.

### 28.1 Example Project

Assume an avionics manufacturer is developing an aircraft airspeed monitoring application.

The software will:

- Receive airspeed data.
- Validate the input.
- Calculate a filtered airspeed value.
- Generate an invalid-data indication.
- Send the processed value to another avionics component.

For this example, assume the approved system safety assessment allocates Level B to the software.

### 28.2 Step 1: Project Initiation

The project manager establishes:

- Project scope
- Software level
- Team structure
- Certification strategy
- Development environment
- Verification resources

### 28.3 Step 2: Planning

Prepare:

- PSAC
- SDP
- SVP
- SCMP
- SQAP

The project team identifies applicable Level B objectives and plans how they will be satisfied.

### 28.4 Step 3: Requirements Development

Example requirements:

| ID | Requirement |
| --- | --- |
| HLR-001 | Receive airspeed data |
| HLR-002 | Validate airspeed input |
| HLR-003 | Calculate filtered airspeed |
| HLR-004 | Generate invalid-data indication |
| HLR-005 | Transmit processed airspeed |

Each requirement is reviewed and traced to the appropriate system requirement.

### 28.5 Step 4: Software Architecture

The software is decomposed into five modules:

1. Input interface module
2. Validation module
3. Filtering module
4. Fault monitoring module
5. Output interface module

Each module has defined inputs, outputs, and responsibilities.

### 28.6 Step 5: Low-Level Requirements

The high-level requirements are decomposed into detailed functional requirements.

Example:

**HLR-002: Validate airspeed input**

Possible LLRs:

- Read the incoming airspeed value.
- Check the specified input validity flag.
- Check the allowed input range.
- Set the output validity status.
- Reject invalid data according to the approved design.

### 28.7 Step 6: Coding

The developers implement the modules in the approved programming language.

They follow the coding standard and place the source code under configuration control.

### 28.8 Step 7: Verification

The verification team performs:

- Requirements reviews
- Design reviews
- Code reviews
- Static analyses
- Requirements-based testing
- Integration testing
- Structural coverage analysis

### 28.9 Step 8: Problem Resolution

Suppose a test discovers that the software accepts an out-of-range airspeed value.

The project:

1. Records the problem.
2. Investigates the cause.
3. Determines affected requirements.
4. Corrects the implementation.
5. Performs regression verification.
6. Updates traceability.
7. Closes the problem report after confirming the correction.

### 28.10 Step 9: Final Configuration

The team establishes the final software baseline.

It identifies:

- Approved source code
- Executable software
- Build environment
- Test results
- Verification evidence
- Configuration index

### 28.11 Step 10: Certification Completion

The project prepares its final accomplishment and configuration documentation and provides the applicable evidence for certification review.

The example illustrates the process. It is not a complete compliance demonstration for a real Level B system.

## 30\. Final Summary and Key Takeaways

### 30.1 The Most Important Concepts

DO-178C is fundamentally about demonstrating confidence in airborne software through a structured and documented development process.

The following ten principles summarize its core philosophy.

**1\. Safety drives software assurance.**

The software level is derived from the system safety assessment, not from the size or complexity of the software.

**2\. Requirements drive development.**

Software should be developed from controlled, reviewed, and verifiable requirements.

**3\. Design must be traceable.**

Software architecture and detailed design must be connected to the applicable requirements.

**4\. Code must implement requirements.**

Source code should implement the approved design and low-level requirements.

**5\. Verification must be systematic.**

Reviews, analyses, and testing must be planned and performed according to the applicable objectives.

**6\. Testing must be requirements-based.**

Testing should demonstrate that software behaves according to its requirements, including relevant abnormal conditions.

**7\. Structural coverage matters.**

Statement, decision, and MC/DC coverage provide different levels of insight into which software structures have been exercised.

**8\. Configuration management is essential.**

The project must maintain control over source code, test data, executable software, and supporting lifecycle information.

**9\. Quality assurance is independent of functional testing.**

SQA provides confidence that the defined processes and standards have been followed.

**10\. Certification requires evidence.**

The final software must be supported by appropriate lifecycle data and compliance records.

# Final Conclusion

DO-178C should be understood as a complete software development assurance framework, not simply a testing standard.

Its central idea is that confidence in airborne software comes from a controlled combination of:

- Correct and complete requirements
- Disciplined software architecture
- Controlled implementation
- Independent verification where required
- Requirements-based testing
- Structural coverage analysis
- Bidirectional traceability
- Configuration management
- Software quality assurance
- Objective certification evidence

The most important mindset for an avionics engineer is:

**Every software requirement must have a justified implementation, every implementation must be appropriately verified, every verification activity must produce evidence, and every delivered software configuration must be controlled.**
